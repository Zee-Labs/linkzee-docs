Die Linkzee-API ist ratenbegrenzt, damit jede Integration einen fairen,
zuverlässigen Anteil an der Kapazität erhält. Es gibt zwei Ebenen:

- **Rate pro Anfrage**, pro Client-IP, als Sicherheitsnetz (allgemein 100
  Anfragen pro Minute, niedriger auf den aufwendigen Routen wie Uploads und
  Importe).
- **Limits pro Store**, im Store gezählt, egal welcher Schlüssel, welcher Agent
  oder welches Netzwerk die Anfrage sendet. Sie schützen die teuren Vorgänge:
  Downloads, Uploads, Importe und Linkvorschauen.

Wenn du Anfragen in einem normalen, ausgewogenen Tempo sendest, wirst du sie
kaum bemerken.

## Wenn du ein Limit überschreitest

Wenn du in kurzer Zeit zu viele Anfragen sendest, antwortet die API mit HTTP
`429 Too Many Requests` im Standard-Fehlerformat:

```json
{
  "error": true,
  "message": "Rate limit exceeded. Please retry shortly.",
  "data": null
}
```

Ein `429` ist vorübergehend. Warte einen Moment, und dieselbe Anfrage gelingt.
Es gehen keine Daten verloren, und für den abgelehnten Aufruf wird nichts
berechnet.

<Note>
Behandle `429` als "versuch es gleich noch einmal", nicht als Fehler. Es
bedeutet, dass du die Obergrenze für dieses Zeitfenster erreicht hast.
</Note>

## Limits pro Store

Dies sind die aktuellen Werte. Sie gelten für die API, für MCP und für die
Upload-Links gleichermaßen.

| Vorgang | Limit |
| --- | --- |
| Eine Bio importieren (`POST /v1/import` mit `mode: "apply"`, MCP `import_bio`) | 3 pro Stunde |
| Eine Seite lesen, um einen Link vorauszufüllen oder eine Importvorschau zu erstellen (`POST /v1/links/parse`, `POST /v1/import` mit `mode: "preview"`, MCP `import_from_url`) | 30 pro Stunde |
| Aus URLs heruntergeladene Bilder | 200 pro Stunde, 1.000 pro Tag, 500 MB pro Tag |
| Aus URLs heruntergeladene Videos | 10 pro Stunde, 30 pro Tag, 600 MB pro Tag |
| Neue Upload-Links | 20 gleichzeitig offen, 60 pro Stunde |
| An Upload-Links gesendete Dateien | 26 pro Minute (Fotos 20, Videos 6), 60 Videos pro Tag, 2.560 MB pro Tag |
| Videos von Linkkarten | 6 pro Minute, 1.536 MB pro Tag |
| Gleichzeitig laufende Downloads | 2; eine dritte Anfrage wartet bis zu 10 Sekunden auf einen freien Platz und erhält dann `429` |

## Idempotency-Keys

Einige Erstellungsvorgänge akzeptieren einen **Idempotency-Key**: einen
eindeutigen Wert, den du für jede logische Erstellung wählst. Wenn nach einem
Timeout, einem `429` oder einem Netzwerkaussetzer erneut versucht wird, gibt die
API zurück, was bereits erstellt wurde, statt es doppelt zu erstellen.

### Wo er gilt

| Vorgang | Key |
| --- | --- |
| `POST /v1/products` | Optional, Header `Idempotency-Key` |
| `POST /v1/agenda/packages` | **Erforderlich**, Header `Idempotency-Key` oder Body-Feld `idempotencyKey` |
| `POST /v1/agenda/subscription-plans` | **Erforderlich**, Header oder Body-Feld |
| `POST /v1/import` mit `mode: "apply"` | **Erforderlich**, Header oder Body-Feld |
| MCP `create_link`, `create_product`, `create_products_bulk` (pro Element), `create_appointment`, `create_lead` | Optional, Argument `idempotencyKey` |
| MCP `manage_package` mit `op: "create"`, `import_bio` | **Erforderlich**, Argument `idempotencyKey` |

Wenn sowohl der Header als auch das Body-Feld gesendet werden, gewinnt der
Header. Keys sind bis zu 200 Zeichen lang.

### Wie er sich verhält

| Situation | Ergebnis |
| --- | --- |
| Erste Anfrage mit einem neuen Key | Erstellt das Element und merkt sich den Key 24 Stunden lang. |
| Derselbe Key, derselbe Body, innerhalb von 24 Stunden | Gibt das beim ersten Mal erstellte Element zurück (ein Import antwortet mit `replayed: true`). Es wird nichts Neues erstellt. |
| Derselbe Key, **anderer** Body | `409 Conflict`. Verwende einen neuen Key für ein neues Element. |
| Derselbe Key, während die erste Anfrage noch läuft | Wartet einige Sekunden, bis die erste fertig ist, und gibt ihr Ergebnis zurück, oder `409`, wenn es zu lange dauert. Versuch es nach einem Moment erneut. |
| Key fehlt, wo er erforderlich ist | `400 Bad Request`. |

Ein Key gehört zu deinem Store, zum API-Schlüssel (oder zur Verbindung), der
ihn gesendet hat, und zum Vorgang, sodass derselbe Wert in einem anderen
Vorgang nicht kollidiert.

```bash
curl -X POST \
  -H "Authorization: Bearer lzk_your_key" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 8f3a1c22-catalog-import-042" \
  -d '{"name":"Wireless Earbuds","url":"https://shopee.com.br/..."}' \
  https://api.linkz.ee/v1/products
```

## Bewährte Vorgehensweisen

### Erneut versuchen mit Backoff

Wenn du ein `429` erhältst, pausiere vor dem erneuten Versuch und verlängere die
Pause bei jedem weiteren Fehlschlag (exponentieller Backoff). Füge etwas Zufall
hinzu ("Jitter"), damit viele Clients nicht im Gleichschritt erneut versuchen.

```bash
# Retry with growing delays: 1s, 2s, 4s, 8s...
attempt=0
until response=$(curl -sf -X GET \
  -H "Authorization: Bearer lzk_your_key" \
  https://api.linkz.ee/v1/products); do
  attempt=$((attempt + 1))
  [ "$attempt" -ge 5 ] && break
  sleep $(( 2 ** (attempt - 1) ))
done
```

### Verteile deine Anfragen

Verteile die Arbeit, statt alles auf einmal abzufeuern. Wenn du einen großen
Katalog synchronisierst, füge eine kleine Verzögerung zwischen den Aufrufen ein,
statt Hunderte parallel zu senden. Gleichmäßig schlägt stoßweise.

### Einmal abrufen, lokal wiederverwenden

Lese-Endpunkte geben den vollständigen aktuellen Zustand zurück (zum Beispiel
deine Produkt- oder Linkliste). Rufe ihn einmal ab, behalte ihn im Speicher und
arbeite mit deiner lokalen Kopie, statt dieselben Daten in einer Schleife
anzufordern.

<Warning>
Die Limits können sich im Laufe der Zeit ändern, wenn wir die Kapazität
anpassen. Baue deinen Client so, dass er auf eine `429`-Antwort reagiert, statt
eine feste Anzahl von Anfragen pro Sekunde fest einzuprogrammieren.
</Warning>
