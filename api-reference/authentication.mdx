The Linkzee API lets you manage your page, product showcase, links, bookings and
more from your own code. Every request is a plain HTTPS call that returns JSON,
authenticated with an API key.

## Base URL

All endpoints live under `/v1` on a single host:

```
https://api.linkz.ee/v1
```

Send bodies as `application/json`. Every response comes back as JSON too.

## Your API key

Authenticate every request with a bearer token in the `Authorization` header:

```
Authorization: Bearer lzk_your_key
```

Linkzee keys always start with the `lzk_` prefix. Create and manage keys from the
API keys screen in your account.

<Warning>
  Treat your key like a password. It carries full access to the data of the store
  it belongs to — keep it server-side, never commit it to a repository, and
  rotate it if it leaks.
</Warning>

### Which store a key acts on

One Linkzee account can hold **several stores** (see
[Multiple stores](/account/multiple-stores)). A key is bound to a **single
store**: the one that was active in the dashboard when the key was created.
Every `/v1` request made with that key — and every MCP call — reads and writes
that store, and only that store.

There is **no request header to pick a store**. To automate a second store,
switch to it in the dashboard, create a key there, and use that key.

<Note>
  Rotating a key keeps it on the same store as the original, so an integration
  never silently moves to another store. A key created before stores could be
  separated isn't bound to one: it acts on the account's **oldest** store until
  you replace it with a store-bound key.
</Note>

### Scopes

Each key has a scope that controls what it can do:

| Scope | Grants |
| --- | --- |
| `read` | Read-only access — every `GET` except financial reports. |
| `write` | Everything `read` allows, plus create, update, delete and reorder (`POST`, `PATCH`, `PUT`, `DELETE`). |
| `finance` | Financial reports (`GET /v1/agenda/earnings`). Never included by default — add it explicitly when creating the key. |

A `read` key sent to a write operation is rejected with `403 Forbidden`. Give each
integration the narrowest scope it needs.

## Making a request

Here's a quick health check you can run to confirm your setup — it needs no key
and returns the standard envelope:

```bash
curl https://api.linkz.ee/health
```

```json
{
  "error": false,
  "message": "API is up",
  "data": { "status": "ok" }
}
```

An authenticated call looks the same, with your key attached:

```bash
curl -H "Authorization: Bearer lzk_your_key" \
  https://api.linkz.ee/v1/store
```

## Response envelope

Every response uses one consistent shape, so you can parse success and failure the
same way.

<Note>
  The `message` field is a human-readable label. **Success** messages are in
  English (part of the stable API contract); **error** messages are localized to
  your request (send the `x-lang` header; default pt-BR). Program against `error`,
  `statusCode` and `code`, never the `message` string.
</Note>

### Success

Successful responses always have `error: false`, a human-readable `message`, and a
`data` payload (which may be `null` for actions like delete):

```json
{
  "error": false,
  "message": "Store loaded successfully",
  "data": { }
}
```

### Errors

Failures set `error: true` and add a few fields to help you debug:

```json
{
  "error": true,
  "statusCode": 401,
  "message": "Chave de API ausente.",
  "path": "/v1/store",
  "timestamp": "2026-07-21T14:03:11.482Z"
}
```

| Field | Description |
| --- | --- |
| `error` | Always `true` on failures. |
| `statusCode` | The HTTP status, repeated in the body. |
| `message` | A readable explanation of what went wrong. |
| `fields` | Present on validation errors: a map of `{ field: reason }`. |
| `code` | Optional short code to distinguish two errors that share a status. |
| `path` | The request path that failed. |
| `timestamp` | When the error occurred (ISO 8601). |

<Note>
  On validation failures the `fields` object tells you exactly which inputs were
  rejected and why, so you can surface precise messages in your own app.
</Note>

## Status codes

| Status | Meaning |
| --- | --- |
| `200 OK` | The request succeeded. |
| `201 Created` | A new resource was created. |
| `400 Bad Request` | The request body or parameters were invalid — check `fields`. |
| `401 Unauthorized` | The key is missing, malformed, revoked or invalid. |
| `403 Forbidden` | The key is valid but its scope doesn't allow this operation. |
| `404 Not Found` | The resource doesn't exist or isn't yours. |
| `429 Too Many Requests` | You've hit the rate limit — back off and retry. |
