The content endpoints expose what a visitor sees in the links zone of a page:
loose links, collections (groups of links) and AI assistant items, plus a `meta`
block that summarizes the product showcase (counters, category chips, featured
products and the first page of the catalog).

All requests go to `https://api.linkz.ee` and must include your API key:

```
Authorization: Bearer lzk_your_key
```

<Note>
Products are not part of the reorderable tree. The showcase follows its own
order (newest first, or the manual order set with
[`PUT /v1/products/order`](/api-reference/products)). Product entries sent to the
reorder endpoint are ignored.
</Note>

## Get content tree

```
GET /v1/content
```

Returns the content tree of your page, plus a `meta` summary of the product
showcase. It is the owner view: it answers even when the page is hidden, and
then `pageHidden` is `true` (the public page returns `404` in that case).

### Request

```bash
curl -X GET \
  -H "Authorization: Bearer lzk_your_key" \
  https://api.linkz.ee/v1/content
```

### Response

The `data` object has three parts: `meta` (showcase summary), `root` (the ordered
list of content entries, each one a `link`, a `collection` or an
`ai_assistant`) and `pageHidden`.

<Note>
When the showcase is hidden, the `meta` counters return `0` and `featured`,
`categories` and `catalog.items` come back empty. Empty collections (no active
children) are dropped from `root`. Special cards (map, reviews, services and the
others) are not part of this response; their position is set with the reorder
endpoint below.
</Note>

A few fields worth knowing: `highlightFx` is a string, `""` (none), `"shake"`,
`"shine"`, `"pulse"` or `"bounce"` (the Premium animated highlight); `cardSize`
is `"normal"` or `"wide"` (a wide card spans both grid columns); `imageRatio` is
the image width divided by its height (`1` for square); and `order` is the
product position, used by the catalog cursor in manual order.

## Reorder content

```
PUT /v1/content/order
```

Sets the order of the links zone in one call: links, collections, AI assistants
and the special cards. Each entry's position in the array becomes its new order.
Requires a key with the **write** scope. The MCP tool `reorder_content` uses the
same rules, and `get_content_tree` returns the tree in this exact format.

### Request

```bash
curl -X PUT \
  -H "Authorization: Bearer lzk_your_key" \
  -H "Content-Type: application/json" \
  -d '{
    "root": [
      { "type": "link", "id": "507f1f77bcf86cd799439011" },
      { "type": "section", "key": "services" },
      {
        "type": "collection",
        "id": "507f1f77bcf86cd799439020",
        "children": [
          { "type": "link", "id": "507f1f77bcf86cd799439012" },
          { "type": "ai_assistant", "id": "507f1f77bcf86cd799439030" }
        ]
      },
      { "type": "section", "key": "reviews" },
      { "type": "section", "key": "map" }
    ]
  }' \
  https://api.linkz.ee/v1/content/order
```

### Parameters

| Parameter | Type | Required | Description |
| --- | --- | --- | --- |
| `root` | array | Yes | Top level entries in their new order. May be empty. |
| `root[].type` | string | Yes | `link`, `collection`, `ai_assistant`, `section` or `product` (ignored). |
| `root[].id` | string | Except for `section` | The entry's ID. |
| `root[].key` | string | With `section` | The special card: `carousel`, `map`, `tips`, `review` (Google review), `reviews`, `packages`, `services`, `instagram` or `social:<network>` (for example `social:instagram`). |
| `root[].children` | array | No | Child items, in order. Only used when `type` is `collection`. |
| `root[].children[].type` | string | Yes | `link`, `ai_assistant` or `product` (ignored). |
| `root[].children[].id` | string | Yes | The child item's ID. |

### How the server applies the tree

- **Incomplete tree.** Links and collections you leave out are not lost: they
  keep their place next to their old neighbors. The children of a collection sent
  without `children` stay as they are. AI assistants move only when they are in
  the tree.
- **Special cards.** With at least one `section` in the tree, the server
  recalculates the position of **every** special card on the page (the cards you
  left out keep their relative place). Without any `section`, the cards are not
  touched.
- **Invalid entries never fail the call.** They are skipped and reported in
  `warnings`:

| Warning | Meaning |
| --- | --- |
| `section_not_on_page:<key>` | The card is not on the page (for example, no map address). |
| `unknown_item:<id>` | No link or AI assistant with this ID in your store. |
| `unknown_collection:<id>` | No collection with this ID in your store. |
| `media_block_not_in_collection:<id>` | A media block cannot go inside a collection; it stays at the root, right after it. |

<Warning>
The items are saved first, then the card positions. In the rare case of a failure
between the two writes, the items are already in the new order and the cards
keep their previous position; sending the same tree again fixes it.
</Warning>

### Response

```json
{
  "error": false,
  "message": "Content reordered successfully",
  "data": {
    "ok": true,
    "warnings": ["section_not_on_page:map"]
  }
}
```

`warnings` is present only when something was skipped.
