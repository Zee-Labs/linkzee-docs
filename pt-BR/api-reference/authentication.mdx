A API do Linkzee permite gerenciar sua página, vitrine de produtos, links, agendamentos e
muito mais a partir do seu próprio código. Toda requisição é uma simples chamada HTTPS que retorna JSON,
autenticada com uma chave de API.

## URL base

Todos os endpoints ficam sob `/v1` em um único host:

```
https://api.linkz.ee/v1
```

Envie os corpos como `application/json`. Toda resposta também volta em JSON.

## Sua chave de API

Autentique cada requisição com um token bearer no cabeçalho `Authorization`:

```
Authorization: Bearer lzk_your_key
```

As chaves do Linkzee sempre começam com o prefixo `lzk_`. Crie e gerencie suas chaves na
tela de chaves de API da sua conta.

<Warning>
  Trate sua chave como uma senha. Ela dá acesso total aos dados da sua conta —
  mantenha-a no servidor, nunca faça commit dela em um repositório e troque-a caso vaze.
</Warning>

### Escopos

Cada chave tem um escopo que controla o que ela pode fazer:

| Escopo | Concede |
| --- | --- |
| `read` | Acesso somente leitura. Todas as requisições `GET`. |
| `write` | Tudo que `read` permite, além de criar, atualizar, excluir e reordenar (`POST`, `PATCH`, `PUT`, `DELETE`). |

Uma chave `read` enviada para uma operação de escrita é rejeitada com `403 Forbidden`. Dê a cada
integração o escopo mais restrito de que ela precisa.

## Fazendo uma requisição

Aqui está uma verificação de saúde rápida que você pode executar para confirmar sua configuração — ela não precisa de chave
e retorna o envelope padrão:

```bash
curl https://api.linkz.ee/health
```

```json
{
  "error": false,
  "message": "API no ar",
  "data": { "status": "ok" }
}
```

Uma chamada autenticada é parecida, com sua chave anexada:

```bash
curl -H "Authorization: Bearer lzk_your_key" \
  https://api.linkz.ee/v1/store
```

## Envelope de resposta

Toda resposta usa um formato consistente, para que você possa tratar sucesso e falha da
mesma maneira.

<Note>
  O campo `message` é um rótulo legível, atualmente retornado em **português**
  independentemente do idioma (ex.: `"Loja carregada"`). Trate-o como texto de
  exibição — decida no seu código por `error`, `statusCode` e `code`, nunca pela
  string `message`.
</Note>

### Sucesso

Respostas bem-sucedidas sempre têm `error: false`, uma `message` legível e um
payload `data` (que pode ser `null` para ações como exclusão):

```json
{
  "error": false,
  "message": "Loja carregada",
  "data": { }
}
```

### Erros

Falhas definem `error: true` e adicionam alguns campos para ajudar você a depurar:

```json
{
  "error": true,
  "statusCode": 401,
  "message": "Chave de API ausente.",
  "path": "/v1/store",
  "timestamp": "2026-07-21T14:03:11.482Z"
}
```

| Campo | Descrição |
| --- | --- |
| `error` | Sempre `true` em falhas. |
| `statusCode` | O status HTTP, repetido no corpo. |
| `message` | Uma explicação legível do que deu errado. |
| `fields` | Presente em erros de validação: um mapa de `{ field: reason }`. |
| `code` | Código curto opcional para distinguir dois erros que compartilham o mesmo status. |
| `path` | O caminho da requisição que falhou. |
| `timestamp` | Quando o erro ocorreu (ISO 8601). |

<Note>
  Em falhas de validação, o objeto `fields` informa exatamente quais entradas foram
  rejeitadas e por quê, para que você possa exibir mensagens precisas no seu próprio app.
</Note>

## Códigos de status

| Status | Significado |
| --- | --- |
| `200 OK` | A requisição foi bem-sucedida. |
| `201 Created` | Um novo recurso foi criado. |
| `400 Bad Request` | O corpo ou os parâmetros da requisição eram inválidos — confira `fields`. |
| `401 Unauthorized` | A chave está ausente, malformada, revogada ou inválida. |
| `403 Forbidden` | A chave é válida, mas seu escopo não permite esta operação. |
| `404 Not Found` | O recurso não existe ou não é seu. |
| `429 Too Many Requests` | Você atingiu o limite de requisições — recue e tente novamente. |
